# Произвольная частота CSV, замедление и лимиты

В `notebooks/csv_single_dual.ipynb` частота точек CSV не связана с частотой ServoJ.
Контроллер интерполирует по времени и отправляет команды с `COMMAND_HZ` (по умолчанию
125 Гц). `READ_HZ` задаётся независимо. CSV может содержать любую частоту, в том числе
неравномерные возрастающие timestamps. Углы — rad, время — секунды.
Если CSV плотнее командной сетки, контроллер выбирает интерполированное задание
на своих тактах: это не обещание отправить каждую строку CSV отдельной командой.

## Настройки ноутбука

| Поле | По умолчанию | Смысл |
|---|---|---|
| `CSV_TIME_COLUMN` | `"t"` | Столбец времени; `None`, если его нет |
| `CSV_SOURCE_HZ` | `None` | Частота исходных строк **только без столбца времени**, например `100.` |
| `CSV_ZERO_START` | `True` | Вычитает первый timestamp, сохраняя интервалы; исключает неявный подвод до первого времени CSV |
| `CSV_RESAMPLE_HZ` | `None` | Не менять точки; например `30.` — пересчитать/выбрать точки до замедления |
| `CSV_RESAMPLE_MODE` | `"interpolate"` | Точная сетка или `"select"` — только исходные строки |
| `TIME_SCALE` | `1.0` | `2.` — вдвое медленнее; `3.` — втрое; значение должно быть положительным |

Для `100 → 30 Гц` со строгой сеткой:
```python
CSV_RESAMPLE_HZ = 30.0
CSV_RESAMPLE_MODE = "interpolate"
```
При positions-only CSV новые углы вычисляются линейной интерполяцией. Если важно
не создавать новых значений, выберите `"select"`: сохраняются ближайшие исходные
строки **и их исходное время**. Для 100 → 30 Гц это примерно 30/40/30 мс, а не
строго 33.333 мс. Обе конечные точки сохраняются; последний интервал может быть короче.
Фильтрации нет: downsampling может потерять экстремумы/детали и изменить путь.
После подготовки остаётся проверка коллизий отправляемой траектории.

Замедление идёт после resampling: `TIME_SCALE=3` превращает 30 Гц точек в 10 Гц,
увеличивает время втрое, уменьшает скорость втрое и оценку ускорения в девять раз.
ServoJ при этом остаётся на 125 Гц. Для сохранения **итоговых** 30 Гц можно поменять
порядок в Python API:
```python
raw = Trajectory.from_csv(path, joint_names, arm="both")
slow = raw.time_scaled(3)
slow_30hz = slow.resampled(30)  # Дополнительные точки уже замедленной траектории.
```
`from_csv()` по умолчанию сохраняет время; нормализацию начала делает именно ноутбук.
Все преобразования возвращают копии. Производные не добавляются в positions-only
payload. Если dq/ddq были явно заданы пользователем, `time_scaled(n)` делит их на n/n².

## Лимиты и графики

`LEFT_LIMITS` и `RIGHT_LIMITS` содержат по шесть значений в SDK-порядке J1…J6:
`min_position`, `max_position` (rad), `max_velocity` (rad/s),
`max_acceleration` (rad/s²), `max_step` (rad/отправленную команду).
Например:
```python
LEFT_LIMITS["max_velocity"] = [0.5] * 6
RIGHT_LIMITS["max_acceleration"] = [1.0] * 6
```
Эти значения передаются в `Arm`, не только рисуются. Позиционные и скоростные пределы
пересекаются с URDF — большими числами в настройках нельзя расширить пределы URDF.
После изменения настроек закройте завершивший работу `robot`, затем заново создайте
его и подключите. Перед CSV проверяются настройки **подключённого** экземпляра.

Новая offline-ячейка до подключения строит для каждой руки 6×3 графика q/dq/ddq,
рисует действующие лимиты и красные точки превышений. Время preview относительное:
будущий UTC-start ещё не назначен. Графики выполнения по-прежнему используют UTC.

Для positions-only CSV dq — точная скорость линейного сегмента, ddq — **численная
оценка** изменения соседних скоростей по расстоянию между серединами сегментов.
При менее чем трёх точках оценка ускорения отсутствует, а не подменяется нулями/NaN.
В узлах, на старте и финише возможны скачки скорости: конечный график не гарантирует
непрерывного ограничения ускорения. C++ ограничивает ускорение интерполяционного
полинома; внутри линейных сегментов оно нулевое и не отражает эти скачки.

Перед CSV ноутбук блокирует известные превышения q/v и **оценки** a. Встроенный
пример CSV на исходной скорости превышает текущие консервативные пределы оценки a;
`TIME_SCALE=2` проходит эту offline-проверку без повышения лимитов. Это не гарантия
динамики реального робота. Производные preview не отправляются и не превращают CSV
в сглаженные cubic/quintic-сегменты. `max_step`, свежесть feedback и остальные
защиты контроллера остаются независимыми; успешный preview не отменяет их.

RRTConnect пока использует позиционные границы URDF, а не суженные пользовательские
границы при поиске. Выход плана за более узкие `Arm`-лимиты может привести к отказу
при отправке; автоматического перепланирования с ними не добавлено.

## Обновление и проверка

Функции входят в обновлённые `wheelhouse/` для Python 3.10–3.15 на Linux/Windows.
Версия осталась `0.1.0`: переустановите подходящий вашей ОС/ABI файл с
`python -m pip install --force-reinstall --no-deps <путь-к-wheel>`, затем перезапустите
ядро Jupyter. Старые wheels без этого обновления не содержат новых функций.
Подробная матрица: [WHEEL_MATRIX.md](WHEEL_MATRIX.md).

108 тестов прошли на каждом из 12 wheels. Новый notebook single/dual выполнен
с локальными mock-роботами на Linux/Windows CPython 3.12 при TIME_SCALE=2;
реальное оборудование не подключалось. C++ и SDK при этом не пересобирались.
